手填LR分析表时，最容易卡在这样一格：圆点后面是等号，好像该移进；同一个状态里又有圆点在末尾的项目，好像该归约。两个动作是不是一定会撞上？先不用重画整张表，只看这格对应的下一个输入符号。

## 1. 一个状态里同时有两种项目，不一定冲突

先用个短文法：`S → Ab | ac`，`A → a`。从初态读入`a`后，状态里有`S → a·c`和`A → a·`。前者在看到`c`时要求移进。后者表示`a`已经匹配完，但SLR只会在`FOLLOW(A)`里的符号上填归约。

文法中`A`只出现在`Ab`里，所以`FOLLOW(A) = {b}`。这一行的`b`列填`A → a`归约，`c`列填移进。两种动作放在同一行，没有挤进同一格。

## 2. FOLLOW集有时会把别处的符号也带过来

换成经典的赋值文法：

```text
S → L = R | R
L → * R | id
R → L
```

从初态沿`L`转移，来到包含`S → L·=R`和`R → L·`的状态。第一项仍然很直观：下一符号是`=`就移进。麻烦在第二项。因为`S → L=R`里`L`后面是`=`，而`L → *R`里的`R`在末尾，所以这个`=`会从`FOLLOW(L)`传进`FOLLOW(R)`。按SLR填表，`=`列既要移进，又要用`R → L`归约，这才是真的移进／归约冲突。

## 3. LALR会看这一个归约项目能跟什么

再回到初态。这里的`R → ·L`来自`S → ·R`。这个`R`已经是产生式末尾，沿用的是输入结束符`#`。沿`L`转移后，完成项目是`[R → L·, #]`，它只要求在`#`列归约。在这个例子里，没有另一个同心状态会给这项并进`=`。因此LALR合并完成后，`=`列仍然只移进，`#`列才填`R → L`归约。LALR会合并同心状态的展望符，并不保证所有文法合并后都没有冲突。

以后手算遇到一格填不下，先写下那一列的符号，再问两个问题：移进是由哪个点后的终结符要求的？归约又是从全局FOLLOW集，还是从这个项目的展望符拿到它的？把这两处圈出来，通常就知道该回头检查哪一步。

经典赋值文法见Aho等《编译原理》第2版，§4.6.4。关于LALR和规范LR的区别，可参看[GNU Bison手册](https://www.gnu.org/software/bison/manual/bison.html#LR-Table-Construction)。
